2. Tell me about a difficult technical problem.
When designing a UVM testbench for the fetch stage of a pipelined CPU, I had to define the reset contract between different modules.
I had to separate concerns among the driver, transaction, monitor, scoreboard, and test.
At first, I included the reset signal as part of the transaction that goes into the DUT (fetch stage).
And the monitor sampled at every cycle.
This worked at first, but then introduced issues when I wanted to test reset behaviour in between cycles.
It also doesn't make sense architecturally, since reset in a pipelined CPU would be controlled globally rather than on a per-cycle basis.
To fix this, I created a UVM reset sequence dedicated to toggling the reset signal.
Now, all I was able to control reset from a higher level (the test level), and one that is more accurate to the real-world usage.
Another big problem when designing my testbenches was when the monitor should sample the DUT and send that sample to the scoreboard.
At first I designed it to only sample when a valid transaction was driven.
But this broke quickly again when I wanted to test reset behaviour and stall behaviour.
I fixed this by instead sampling every clock, and letting the scoreboard decide whether it should be counted as a valid transaction or not.

Fixed:
While building a UVM testbench for the fetch stage of a pipelined CPU, I ran into two related issues around how reset and sampling should be modeled in a verification environment.
Initially, I modeled reset as part of the transaction being driven into the DUT, since I was thinking of everything as a single stimulus stream. The monitor also only sampled when a valid transaction was present.
This worked for basic functionality, but it started breaking down when I tried to test reset behavior and pipeline stalls. Reset is not really a per-transaction concept in a pipelined CPU — it’s a global control signal that can occur independently of instruction flow. Because of that, embedding it in transactions made it impossible to correctly model reset happening between cycles.
To fix this, I separated reset into its own UVM sequence that directly controlled the reset signal at the test level, independent of instruction transactions. That made the reset behavior realistic and reusable across different test scenarios.
I also updated the monitor logic. Instead of sampling only when a valid transaction was driven, I made it sample every clock cycle. Then I pushed the responsibility of filtering valid behavior into the scoreboard.
That change made the testbench more robust because it allowed me to correctly capture edge cases like reset and stalls without losing visibility into DUT behavior at the cycle level.

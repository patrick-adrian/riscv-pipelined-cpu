2. Tell me about a difficult technical problem.

While building a UVM testbench for the fetch stage of a pipelined CPU, I ran into two related issues around how reset and sampling should be modeled in a verification environment.
Initially, I modeled reset as part of the transaction being driven into the DUT, since I was thinking of everything as a single stimulus stream. The monitor also only sampled when a valid transaction was present.
This worked for basic functionality, but it started breaking down when I tried to test reset behavior and pipeline stalls. Reset is not really a per-transaction concept in a pipelined CPU — it’s a global control signal that can occur independently of instruction flow. Because of that, embedding it in transactions made it impossible to correctly model reset happening between cycles.
To fix this, I separated reset into its own UVM sequence that directly controlled the reset signal at the test level, independent of instruction transactions. That made the reset behavior realistic and reusable across different test scenarios.
I also updated the monitor logic. Instead of sampling only when a valid transaction was driven, I made it sample every clock cycle. Then I pushed the responsibility of filtering valid behavior into the scoreboard.
That change made the testbench more robust because it allowed me to correctly capture edge cases like reset and stalls without losing visibility into DUT behavior at the cycle level.

3. Tell me about a difficult challenge.
I had to come up with ways to performance test an API request/response microservice.
I needed to design tests that isolated different stress points of our system.
To do this, I changed one variable per test.
1. Connection Scalability Test: vary number of clients, each client sends one request, meaure latency and number of errors. 
2. Throughput Saturation Test: vary RPS, fix number of clients, measure latency and number of errors.
3. Mixed Scaling Test: vary number of clients and RPS, measure latency and number of errors.
With each test, I was able to stress different sections of the system and isolate which ones were the bottleneck.
This led to architectural improvements, such as to NGINX, and I was able to validate improvement with the same tests.

3. Tell me about a time you worked on a team.
In one of my major projects, I worked in a small team building a 32-bit RISC CPU on an FPGA using VHDL. My role focused on the datapath and control integration, while other team members worked on instruction memory and individual modules like ALU and register file design.
Early on, we ran into integration issues where each module worked independently, but the full system wasn’t behaving correctly when combined. The main problem was inconsistent assumptions about timing and signal validity between modules.
To address this, we started aligning on a shared interface contract for signals like valid/ready behavior and clocked updates. I also took responsibility for helping debug system-level issues using simulation waveforms, tracing signals across module boundaries instead of only looking at individual blocks.
Over time, this improved our integration process significantly and reduced debugging time because we were no longer treating modules in isolation.
From that experience, I learned that in hardware systems, most team issues aren’t about individual module correctness—they’re about interface assumptions and communication between component

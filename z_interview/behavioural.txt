2. Tell me about a difficult technical problem.

While building a UVM testbench for the fetch stage of a pipelined CPU, I ran into two related issues around how reset and sampling should be modeled in a verification environment.
Initially, I modeled reset as part of the transaction being driven into the DUT, since I was thinking of everything as a single stimulus stream. The monitor also only sampled when a valid transaction was present.
This worked for basic functionality, but it started breaking down when I tried to test reset behavior and pipeline stalls. 
Reset is not really a per-transaction concept in a pipelined CPU — it’s a global control signal that can occur independently of instruction flow. 
Because of that, embedding it in transactions made it impossible to correctly model reset happening between cycles.
To fix this, I separated reset into its own UVM sequence that directly controlled the reset signal at the test level, independent of instruction transactions. 
That made the reset behavior realistic and reusable across different test scenarios.
I also updated the monitor logic. Instead of sampling only when a valid transaction was driven, I made it sample every clock cycle. Then I pushed the responsibility of filtering valid behavior into the scoreboard.
That change made the testbench more robust because it allowed me to correctly capture edge cases like reset and stalls without losing visibility into DUT behavior at the cycle level.

3a. Tell me about a difficult challenge.

One difficult challenge I worked on was designing performance tests for an API request/response microservice at Evertz.
The problem was that we needed meaningful benchmark data, but it was hard to identify where performance bottlenecks were actually coming from because multiple factors could affect the system at once.
To solve this, I designed a set of tests where I changed one variable at a time so we could isolate different stress points in the architecture.
For example:
In a connection scalability test, I varied the number of clients while keeping request behavior simple, then measured latency and error rates.
In a throughput saturation test, I fixed the number of clients but increased requests per second to identify throughput limits.
I also created mixed scaling tests where both client count and request rate increased together to simulate more realistic production behavior.
By comparing the results across these tests, we were able to isolate which parts of the system became bottlenecks under different conditions.
That led to architectural improvements, including changes to NGINX configuration and request handling behavior. 
After the changes, I reran the same automated tests to validate that latency and scalability improved as expected.
I learned a lot from that experience about designing controlled experiments, interpreting performance data, and building tests that are actually useful for engineering decisions rather than just generating numbers.

3. Tell me about a time you worked on a team.
In one of my major projects, I worked in a small team building a 32-bit RISC CPU on an FPGA using VHDL. 
My role focused on the datapath and control integration, while other team members worked on instruction memory and individual modules like ALU and register file design.
Early on, we ran into integration issues where each module worked independently, but the full system wasn’t behaving correctly when combined. 
The main problem was inconsistent assumptions about timing and signal validity between modules.
To address this, we started aligning on a shared interface contract for signals like valid/ready behavior and clocked updates. 
I also took responsibility for helping debug system-level issues using simulation waveforms, tracing signals across module boundaries instead of only looking at individual blocks.
Over time, this improved our integration process significantly and reduced debugging time because we were no longer treating modules in isolation.
From that experience, I learned that in hardware systems, most team issues aren’t about individual module correctness—they’re about interface assumptions and communication between component
